**Status:** planned 2026-09-01. Base: `origin/main` (post-B5, all three B5 slices merged, PR #424).
**Milestone:** [B6](2026-08-20-readarr-replacement-roadmap.md#b6--readarr-migration-adoption-preview-and-e-book-cutover)
of the [Readarr replacement roadmap](2026-08-20-readarr-replacement-roadmap.md).
**Governing spec:** [the B0 parity contract](../specs/2026-08-20-books-parity-contract.md) and the
[Bookshelf inventory audit](../audits/2026-08-20-bookshelf-inventory.md) — between them they own the

## What B5 left, and what B6 owns

B5 shipped monitoring, retry, and per-author bulk-monitoring policy for works Cinder already knows
about (`Cinder.Books.set_author_policy/3`, `preview_author_policy/2`, `apply_author_policy/4`,
`Cinder.Books.BibliographyRefresher`). None of that touches an external Radarr-family source. B6 is
a different track — it is the only milestone that talks to Bookshelf at all — but it leans on B5b's
author-policy machinery directly (§3.4 below) rather than rebuilding a second bulk-monitoring path,
so it is not starting from zero.

The existing (movies/TV) migration subsystem B6 extends, read in full before this plan was written:
`Cinder.Library.MigrationSource` (behaviour), `MigrationSource.Radarr`/`.Sonarr` (adapters),
`Cinder.Library.MigrationReconciler` (pure TMDB-external-id reconciliation),
`Cinder.Library.MigrationAdoption` (preview/adopt orchestration, `@statuses
[:ready, :needs_decision, :blocked, :already_managed]`), `CinderWeb.LibraryAdoptionLive`
(`/library/adopt`, `live_session :admin`, unchanged by B6), and the four
`{source}_url/_api_key/_remote_path_prefix/_local_path_prefix` settings rows generated by
`Cinder.Settings.Registry`'s `@migration_sources` list.

## §0. Two things the evidence does not settle

**1. Whether Bookshelf's own foreign ids are reusable Hardcover ids.** The deployment runs
`pennydreadful/bookshelf:hardcover` against the `api.bookinfo.pro` Hardcover proxy, and its
`system/status` reports `appName: "Readarr"` — the wire protocol is Readarr v3's `/api/v1`, and
Bookshelf's `book.foreignBookId` / `author.foreignAuthorId` *might* already be Hardcover-namespace
ids, which would let B6 skip straight to `Identity.reference_for(:hardcover, foreign_id)` — one
direct `get_work/1` fetch instead of up to three sequential HTTP requests for a free-text search
(§B6b.2). No B0 evidence measures either of *Cinder's own* call shapes: the audit's 2.7 s p50 and
60–85 ms figures are Bookshelf's own internal search and the metadata proxy's direct-by-id lookup
respectively — a different service and a different call than anything `Cinder.Books.Identity`
makes, so neither number is cited as an estimate for it here. The committed fixture cannot answer
this either — its ids are synthetic placeholders (`"fixture-work-001"`) by design (the B0 sanitizer
replaces every real identity). This is a genuine B0 gap, not a B6 decision to paper over: **the
design below does not depend on the answer.** It resolves every work through
`Cinder.Books.Identity.resolve/1` with a free-text query built from `authorTitle` + `title`
(namespace-agnostic, works whether or not the ids line up), and leaves the direct-reference path as
a possible future optimization an implementer can add once the real deployment's `foreignBookId`
shape is inspected — never guessed here.

**2. Whether Bookshelf's root folder and Cinder's configured `books` root are the same filesystem
path.** The roadmap's own Work list hedges: "Adopt in place where possible. If publication into a
managed root is required, stage and verify it through the normal B4 import path." Neither the
contract nor the audit states which case the real deployment is in, and the *existing* Radarr/Sonarr
migration code has **no** such branch at all — it adopts a movie/episode's path verbatim, trusting
the operator's media-server library section already covers wherever Radarr/Sonarr put it. B6
follows that exact precedent (§3.3) rather than building an unused staging fallback: it fails closed
via `Settings.library_destination_for_path(:ebook, path)` when a candidate's path is outside
every configured `:ebook` root — kind-scoped, not `Settings.library_root_for_path/1`'s any-kind
match, so a translated path that happens to land inside the operator's movies/TV/audiobooks root
is still correctly rejected as outside the books library — and the cutover procedure (§4) makes
"point the `books` root setting at Bookshelf's
existing library path" an explicit precondition. Building the B4-staging fallback for a scenario
with zero observed need in the one real deployment is out of scope; see "What stays out."

Separate, narrower wrinkle worth stating explicitly: by B6, Book MVP has been shipping since B4,
so Cinder's `books` root plausibly already holds independently-acquired files with their own
`book_files` rows before this cutover ever runs. Repointing the `books` root *setting* does not
move or reinterpret those existing rows — `book_files.path` is an absolute path stored once at
import time, independent of whatever the setting currently points at — so nothing already adopted
is orphaned by a later repoint. The real precondition is narrower than "the root must be empty": it
is that **whatever consumer (Booklore) already scans e-books must cover every root Cinder's
`book_files` rows actually reference, old and new** — the runbook (§B6c.3) calls this out as an
explicit check, not an assumption, at the same step it asks the operator to repoint the setting.

## B6a — `Readarr` migration source, settings, generalized dispatch

### 1. Why `Readarr`, not `Bookshelf`

`Radarr`/`Sonarr` are named for the **wire protocol** they speak (`"Radarr v3 migration snapshot
client"`, `"Sonarr v3 migration snapshot client"` — their own moduledocs), not for whatever fork of
that protocol a household happens to run. The deployment's own `/api/v1/system/status` reports
`"appName": "Readarr"` — the API self-identifies as Readarr, matching the protocol-naming
convention exactly. So the new module is `Cinder.Library.MigrationSource.Readarr` at
`lib/cinder/library/migration_source/readarr.ex`, matching the roadmap's own suggested path
verbatim. Its moduledoc says plainly what it actually talks to: "Bookshelf's Readarr v3-compatible
`/api/v1`, currently `pennydreadful/bookshelf:hardcover`" — and `health/0` validates the observed
`branch`/`version` shape the same defensive way `books_b0_inventory.py` already does ("validates
API status version/branch against the deployment evidence instead of hard-coding source values"),
so a Bookshelf upgrade that changes `system/status` shape fails the health check loudly instead of
silently misreading a differently-shaped snapshot.

  `snapshot/0` issues sequential `GET`s (mirrors `radarr.ex`'s simplicity, not `sonarr.ex`'s

## B6b — Provider-neutral contract expansion and bounded, cached preview classification

This is the slice that actually answers "the exact release, profile snapshot... are persisted" —
no, wrong quote; this is the slice that answers **facts item 6**: 842 works, 181 with files, and an
uncapped resolve-per-work loop is the risk B5b already had to design around once
(`Books.preview_author_policy/2`'s `@max_bibliography_candidates` cap). B6b reuses that exact
pattern rather than re-deriving a new one.

### 1. The expanded snapshot contract

`Cinder.Library.MigrationSource`'s existing types are movie/series/episode-shaped:
`movie.file_id`/`episode.file_id` are singular (one file per video item is the common case; Sonarr's
n-to-one multi-episode file is handled by *grouping several episode rows*, not by a plural
`file_ids`). Books invert that cardinality — one work commonly has *multiple* files (159 EPUB + 25
AZW3 + 4 MOBI across 181 works is already >1 file/work on average) — so the natural extension
reverses the reference direction for book files instead of forcing a plural field onto `work`:

```elixir
@type author :: %{
        required(:provider_id) => provider_id(),
        required(:name) => String.t(),
        required(:foreign_id) => String.t() | nil,
        required(:monitored) => boolean(),
        # Readarr's own enum, carried raw for B6c's informational display — never interpreted
        # into a Cinder monitoring decision. See §3.4.
        required(:monitor_new_items) => String.t() | nil
      }

@type work :: %{
        required(:provider_id) => provider_id(),
        required(:author_id) => provider_id(),
        required(:title) => String.t(),
        required(:foreign_id) => String.t() | nil,
        required(:monitored) => boolean()
      }

@type edition :: %{
        required(:provider_id) => provider_id(),
        required(:work_id) => provider_id(),
        required(:isbn13) => String.t() | nil,
        required(:asin) => String.t() | nil,
        required(:monitored) => boolean()
      }
```

`file/0` gains two **optional** fields, populated only when `kind == :book`:
`optional(:work_id) => provider_id()` (the reversed reference — a book file names its work; a
movie/episode file is named *by* its video item) and `optional(:format) => String.t() | nil` (the
raw `bookfile.quality.quality.name`, lowercased — `"epub"` / `"azw3"` / `"mobi"`, or the raw
unrecognized string when Bookshelf reports something else). `snapshot/0`'s existing
`optional(:diagnostics)` list is unchanged — `readarr.ex`'s sequential-fetch shape (no per-item
concurrency, unlike `sonarr.ex`) means a fetch failure is a whole-snapshot `{:error, _}` from the
`with`/`else` chain, exactly like `radarr.ex`, so no book-specific diagnostic kind is needed.
`snapshot/0` also carries `optional(:profiles)` and `optional(:roots)` — Bookshelf's
`qualityprofile`/`rootfolder`/`config/naming` responses, kept **read-only and informational**: B6
never derives a Cinder `media_profiles` row or a naming policy from them (§3.3, §3.5).

### 2. The bounded, cached resolution loop

New module `Cinder.Library.MigrationAdoption.Readarr`
(`lib/cinder/library/migration_adoption/readarr.ex`) — a sibling extraction from
`migration_adoption.ex`, the same "carved out as plain code motion" pattern
`Cinder.Settings.Registry`/`Crypto` already established, not a new top-level namespace. For
movies/TV, the batching happens in `MigrationAdoption.lookups/1` (`migration_adoption.ex:106-122`),
which calls `Cinder.Catalog.TMDB.find_by_external_id/2` once per unique external id and hands the
resulting map to `MigrationReconciler.reconcile/2` — a pure function with no I/O of its own. Books
have no such batchable primitive: `Cinder.Books.Identity.resolve/1` is a real network call issued
one candidate at a time (its free-text path alone walks `Metadata.providers()` calling `search/1`
on each until one answers, then one `get_work/1` — up to 3 sequential HTTP requests per work,
`identity.ex:128-146`; no B0 evidence measures this exact call's latency — the audit's 2.7 s p50 /
60–85 ms figures are Bookshelf's own search and the metadata proxy's *direct* by-id lookup
respectively, neither the path B6 calls). Shoehorning that through `MigrationReconciler`'s "resolve
everything up front, batched" architecture is exactly the uncapped loop the task calls out — so
`migration_reconciler.ex` is **not modified**; it stays movie/TV-only, and books get their own
bounded loop instead (below).

`Readarr.preview/1` classifies every file-bearing work (`snapshot.works` where at least one
`snapshot.files` row has a matching `work_id`) in two passes, mirroring
`Books.preview_author_policy/2`'s own doc almost verbatim:

1. **Cheap, local, no network.** For each file-bearing work, look up
   `book_identifiers{provider: "readarr", kind: "work", foreign_id: work.foreign_id}` — a plain
   indexed `book_identifiers` read (no new table: `provider` is an unconstrained string column
   already holding `"openlibrary"`/`"hardcover"`/`"isbn"`/`"asin"`; `"readarr"` is one more value,
   never written until B6c's adopt step, §B6c.1). A hit resolves the work locally — no HTTP call —
   and the candidate proceeds straight to path/format classification (§3).
2. **Network-bound, capped.** Every work that misses step 1 is a candidate for
   `Cinder.Books.Identity.resolve/1`, called with a free-text query
   (`"#{work.author_title} #{work.title}"`, per §0.1) — but at most
   `Cinder.Books.max_bibliography_candidates/0` (50, the existing public accessor "exposed so the
   UI need not duplicate it" — reused rather than a second magic number) per `preview/1` call.
   Beyond the cap, a work is neither resolved nor blocked; it is simply not yet a candidate, and its
   count surfaces as `preview.remaining` — the identical field name and meaning
   `preview_author_policy/2` already returns.

**Why this is enough, and what "interrupted" costs.** Preview never writes (§4), so it cannot be
made durably resumable across a crash without inventing state nothing else needs — and it doesn't
need to be: on the *first* preview of an unadopted library, `book_identifiers` has no `"readarr"`
rows yet, so step 1 never short-circuits and the full 181 works cost ~4 capped batches (181 ÷ 50).
At up to 3 HTTP requests per work (§2), that first full walk costs at most 543 HTTP requests to the
metadata providers, spread across those 4 batches (~136 requests/batch worst case) — no wall-clock
estimate is asserted, since no B0 evidence measures `Identity.resolve/1`'s real latency against
Open Library/Hardcover; the cap bounds request *volume* and keeps the LiveView responsive
regardless of how long any one request actually takes. The `/library/adopt` LiveView (B6c)
auto-advances through batches with a live `%{resolved:, remaining:}` progress readout and a Cancel
control — an operator who navigates away or whose connection drops simply reruns Preview later and
re-pays the batches not yet reached, nothing is lost because nothing was written. **Across adopt
cycles it is genuinely resumable**: every successful `adopt/2` call (B6c) durably stamps the
`"readarr"` identifier via the same fold `import_resolution/1` already uses (§B6c.1), so a *second*
preview session (today or next week, after partially confirming a first batch) skips every
already-adopted work in step 1 and only pays the network cost for what's left — the realistic
cutover workflow (preview → adopt a wave → come back → preview → adopt more) gets faster each
time, for free, from a mechanism B6c would have to build anyway.

### 3. Classification

**A work step 2 attempted but could not resolve is a candidate too, not a silent drop.**
`Identity.resolve/1` can return `{:unresolved, reason}` or `{:error, :providers_unavailable}`
(`identity.ex:57-60`) for a work with a real file on disk — the contract's locked line is explicit
that this must be "an explained unresolved/held result instead of first-result selection," not an
omission (`books-parity-contract.md:107`). Every work step 2 actually calls `Identity.resolve/1`
for — whether it succeeds or not — becomes a candidate: `:blocked, {:unresolved_identity, reason}`
on failure, classified below on success. This is what actually distinguishes `:blocked` from
`preview.remaining`: `remaining` counts works the cap never reached this call; `:blocked,
:unresolved_identity` counts works the cap *did* reach where Identity could not resolve one.

For each file-bearing work that *did* resolve, group its `snapshot.files` (`kind: :book`) by
`work_id` and classify the group (mirrors `movie_candidate/4`'s cond chain):

- Any file's `format` not in `{"epub", "azw3", "mobi"}` → that file is `:blocked,
  :unsupported_format`; it does not block its siblings (per-file, not per-work, since one bad file
  among two good ones is exactly the multi-format case below, not a whole-work failure).
- More than one accepted-format file remains → `:needs_decision, :multi_format`. Two choices,
  mirroring Sonarr's existing fold/part UI verbatim rather than inventing a third interaction
  pattern: **preferred** (adopt only the EPUB — falling back to AZW3, then MOBI, when EPUB is
  absent — per the contract's explicit "EPUB preferred"; the others are left untouched on disk,
  never deleted, never adopted) or **all formats** (adopt every accepted file as a separate
  `book_files` row under the same target — the schema already allows this, `book_files` has no
  one-row-per-target constraint, by design for multi-part audiobooks).
- The winning file's path already equals an existing `book_files.path` for this exact target →
  `:already_managed` (repeated-adoption idempotency).
- The winning file's path collides with a **different** Cinder work/target's file → `:blocked,
  :path_conflict` (a bulk query mirroring `MigrationAdoption.managed_state/1`, adapted to
  `BookFile`/`BookTarget`).
- The resolved work already has a target with a *different* file recorded → `:blocked,
  :identity_conflict`.
- The resolved work's target is `:held` → `:blocked, :target_held` — an operator's or the poller's
  more recent decision is never silently overridden, the same rule `monitor_target/4`'s `arm/3`
  already enforces.
- The translated path (`PathMapping.translate/3`, same remote/local prefix mechanism `radarr.ex`/
  `sonarr.ex` already use) is outside every configured `:ebook` library root
  (`Settings.library_destination_for_path(:ebook, path)` returns `{:error, :outside_library}` —
  kind-scoped, not `Settings.library_root_for_path/1`'s any-kind match, since a books path
  landing inside a configured movies/TV/audiobooks root is exactly the misconfiguration this
  bucket exists to catch) → `:blocked,
  :outside_library_root` — the fail-closed answer to §0.2.
- Otherwise → `:ready`.

**Edition mapping never blocks.** The winning file's Bookshelf edition (`isbn13`/`asin`) is matched
against the *resolved* work's stored `book_identifiers{provider: "isbn"|"asin"}` rows — an exact
match sets `edition_id`; anything else (no match, no isbn/asin reported) leaves it `nil`. This is
not a gap needing a decision bucket: `book_files.edition_id` is nullable *on purpose*
(`20260831090000_create_book_grabs_and_files.exs`'s own comment — "the contract's 'explicitly
incomplete' signal... inventing an edition to satisfy a foreign key would be the silent fallback the
contract exists to prevent"). Reusing that existing, already-sanctioned null is the honest answer,
not a new needs-decision bucket.

**Monitored, fileless works are not candidates.** 661 of the eBook instance's 842 works (842 − 181)
are monitored with no file — the audit's own first "migration hazard." These never enter
`plan_books/1`'s per-row classification at all (avoiding both a useless 661-row UI list `@page_size
50` would just paginate through, and — more importantly — avoiding re-deriving the exact "back-
catalogue flood" risk the contract warns about). Instead `preview/1`'s summary carries a single
computed count, `deferred_bibliography_count` (`Enum.count(snapshot.works, & &1.monitored and
work_id not in files_by_work)`) — zero network cost, pure snapshot arithmetic — surfaced by B6c as
"661 additional monitored works were not imported; use per-author monitoring policy after cutover"
(§4).

### 4. `preview/1`'s write boundary

`Readarr.preview/1` performs **zero** database writes — `Books.Identity.resolve/1` (`fetch/2`,
`fetch_selected/3`) is already read-only (it calls `provider_module.get_work/1`, never
`import_resolution/1`), so the whole two-pass loop is exactly as read-only as movies' existing

## B6c — Adopt choke-point, `/library/adopt` UI, cutover runbook

### 1. `Cinder.Books.Adoption` — the write choke-point

New module `lib/cinder/books/adoption.ex` (`Cinder.Books.Adoption`) — living in the **books**
domain namespace, mirroring `Cinder.Catalog.Adoption`'s own location (`lib/cinder/catalog/
adoption.ex`) exactly, not the generic `lib/cinder/library/` migration namespace: adoption of a
resolved work into the books catalog is books business logic triggered by a migration, the same
relationship `Catalog.Adoption` already has to `MigrationAdoption`. `lib/cinder/books.ex` is also
modified — two functions change visibility/name, no existing caller's behavior changes (below).

**A nested transaction would poison this one.** `Books.import_resolution/1` is itself
`Repo.transaction(fn -> import_work(work, provider) end, mode: :immediate)` (`books.ex:778-780`),
and `import_work/2`'s call graph reaches `Repo.rollback/1` on ordinary, reachable failures —
`Repo.rollback(:identifier_subject_mismatch)` and `Repo.rollback(changeset)` inside
`update_subject/5`/`insert_subject/4` (`books.ex:965-990`). Calling `import_resolution/1` from
inside `adopt_work/3`'s own transaction would nest a second `Repo.transaction` and rollback
boundary inside the first — exactly the failure mode `Files.record_import/3`'s own comment on
`arm_target/1` names by pointing at `BookTargetTransition.guarded/4`: a rollback inside the inner
transaction "aborts the ENCLOSING transaction too... turns a status mismatch into a poisoned
connection rather than a handleable error" (`files.ex:113-117`). The existing caller,
`import_and_monitor/2` (`books.ex:702-705`), only ever calls `import_resolution/1` at the top
level, never nested — proving the rule, not just stating it. **Fix:** `import_work/2` (already the
non-transactional fold — `upsert_in_tx/5`'s own comment already says it exists "so
`import_resolution/1` can fold a whole work... into one") becomes a public `@doc false` function,
`import_work_in_tx/2`, with the same body; `import_resolution/1` becomes the one-line wrapper
`Repo.transaction(fn -> import_work_in_tx(work, to_string(provider)) end, mode: :immediate)` —
every existing caller is unaffected. A second small public `@doc false` function,
`stamp_identifier_in_tx/3` (work, provider, foreign_id), wraps the existing private
`insert_identifier/2` with `on_conflict: :nothing, conflict_target: [:provider, :kind,
:foreign_id]` — the same idempotent-insert shape `put_normalized_identifier/4` already uses for
ISBN/ASIN. `Cinder.Books.Adoption.adopt_work/3` calls both of these directly, inside its own
transaction, never `import_resolution/1` itself.

`adopt_work(resolution, files, opts \\ [])` — one `Repo.transaction(fn -> ... end, mode:
:immediate)`, matching `import_resolution/1`'s own write-lock-first convention:

1. **Refuse a grab in progress.** A `book_grabs` row for this work's `:ebook` target aborts the
   transaction with `{:error, :grab_in_progress}` — the identical race `pause_target/1` (B5a) closes
   for the same reason: overwriting `book_targets.status` out from under an in-flight download
   orphans it (`Files.record_import/3`'s `arm_target/1` would then match neither `:monitored` nor
   `:available` and silently roll back an already-downloaded file). Reused, not re-derived.
2. `Books.import_work_in_tx(work, provider)` then `Books.stamp_identifier_in_tx(work, "readarr",
   bookshelf_foreign_id)` — both run inside this transaction, not a nested one (see above). Folds
   the work/author/editions into the catalog exactly as B5b's `import_and_monitor/2` already does,
   and durably stamps `book_identifiers{provider: "readarr", kind: "work", foreign_id: <bookshelf
   foreign_id>}` — the only write either function's call graph gains, and what makes B6b's step-1
   fast path work on the next preview.
3. `Books.ensure_target(work, :ebook)` — get-or-create, unchanged.
4. Refuse `:held` outright (`{:error, :target_held}`) — same rule as `monitor_target/4`'s `arm/3`.
5. For each file in `files` (one, from the `preferred` choice, or several from `all formats`):
   insert a `BookFile` row with the **unchanged, untouched source path** — no hardlink, no copy, no
   rename (adopt in place; the contract's "never move, rewrite, or delete a source file" is
   structural here, not a runtime check, because this code path never calls `StageEngine` at all).
   **In-transaction idempotency, not just caller-side re-validation.** `book_files.path`'s unique
   index means a genuine race (two operators adopting the same candidate concurrently, or a retried
   `adopt/2` after a crash between commit and the LiveView acknowledging it) would otherwise hit a
   unique-constraint violation on the second attempt. `Files.insert_conflict/3` already solves
   exactly this ("same target, same path ⇒ replay success," `files.ex:86-102`) and is extracted to
   a small shared `@doc false` function, `insert_or_existing/2` (target, attrs) — reused unchanged
   by both `Files.record_import/3` and `Cinder.Books.Adoption.adopt_work/3` rather than duplicated:
   a different target owning the same path is a real `{:error, :path_conflict}`; this target
   already owning it is a no-op success, matching §B6b/3's own `:already_managed` classification.
6. A guarded status write to `:available`, accepting **`[:unmonitored, :monitored, :available]`**
   as the starting status — deliberately not `arm_target/1`'s own `[:monitored, :available]` guard.
   `arm_target/1`'s guard is correct for *its* caller (`Files.record_import/3`, where a target is
   already `:monitored` mid-grab or `:available` on an import replay) but wrong here: step 3's
   `Books.ensure_target/2` creates a target with `BookTarget`'s schema default, `status:
   :unmonitored` (`book_target.ex:18`; `create_changeset/2` never sets `:status`), and that is the
   status the overwhelming majority of the 181 file-bearing Bookshelf works will actually have —
   nothing in Cinder has monitored them yet. `arm_target/1`'s guard would match zero rows and
   return `{:error, :stale_status}` for essentially every real adoption. The correct precedent is
   `arm/3` (`books.ex:427-437`), which accepts a target's *actual* current status (`:unmonitored`
   → `:monitored`, otherwise left alone) rather than demanding one specific `expect:`. `:held` is
   refused by step 4, so it never reaches this write; the module-local guard (not
   `transition_target/3`) is still the right shape for the same two reasons
   `Files.record_import/3`'s own `arm_target/1` comment gives — a broadcast inside this transaction
   would announce a state a rollback can still undo, and `transition_target/3`'s single-`expect:`
   `Repo.rollback` semantics don't compose with a caller that must accept three possible starting
   statuses, not one.
7. Post-commit: `Books.broadcast({:book_target_updated, target})` — the one existing PubSub event
   shape every other write in `Cinder.Books` already uses; no new topic.

`Readarr.adopt/2` (B6b's module) re-validates each selected candidate against the same
classification function `preview/1` uses (mirroring `MigrationAdoption.revalidate_selected/2`'s
existing "preview and adopt are not atomic with each other" defense) before calling
`Books.Adoption.adopt_work/3`, and is `isolate`-style per candidate — one candidate's failure does
not abort the batch, matching `apply_author_policy/4`'s established contract.

### 3. `docs/readarr-migration.md` — the cutover runbook

The roadmap's six steps, made concrete:

1. **Disable Bookshelf automation.** In Bookshelf's own settings, disable RSS sync and automatic
   search for both instances (audiobook is out of scope for B6, but leaving its automation running
   is safe — B6 never touches it). Note explicitly: this step is operator action inside Bookshelf,
   not a Cinder feature.
2. **Back up.** Bookshelf's SQLite database and config directory; Cinder's own SQLite database
   (already covered by whatever backup the household runs, called out as a precondition, not new
   tooling).
3. **Point Cinder's `books` root setting at Bookshelf's existing library path** (§0.2's
   precondition) and configure the four `readarr_*` settings (§B6a.2) with the household's real
   `base_url`/`api_key`/path prefixes. If Cinder already has independently-acquired e-books under a
   *different* prior root (plausible since Book MVP shipped at B4), that is not a blocker — those
   existing `book_files` rows keep their own absolute paths unchanged — but confirm Booklore's own
   library scan already covers both the prior root and Bookshelf's path before proceeding to
   Preview (§0.2).
4. **Run Preview** on `/library/adopt`, resolve every `:needs_decision` row (multi-format choice)
   and investigate every `:blocked` row (a `:path_conflict`/`:identity_conflict`/
   `:outside_library_root` row means either a real duplicate or a root-configuration mismatch to
   fix before adopting — never a row to force through).
5. **Adopt**, then verify: candidate counts match the audit's 181-works/188-files inventory minus
   whatever legitimately blocked; spot-check a handful of `book_files.path` rows resolve to the
   same bytes on disk (a representative sample hash comparison, per the roadmap's own "Operational
   rehearsal" test-strategy section — not every file, the audit's own 188-file scale makes a full
   sweep cheap enough to do anyway if the operator prefers).
6. **Enable Cinder monitoring** — nothing automatic: newly-adopted targets are `:available` with no
   active search; an operator opts specific works into `:monitored` upgrades, or authors into a
   B5b policy, exactly as any other Cinder-managed work already works.

**Rollback:** re-enable Bookshelf's automation from the step-2 backup. Cinder never deleted, moved,
or rewrote a Bookshelf-managed file — every adopted `book_files.path` is byte-identical to what
Bookshelf already had — so rollback is purely "start Bookshelf's automation again," not a data
migration in reverse.

### 4. Data model

None, again. B6c's only new write is the `book_identifiers` "readarr" stamp (§1.2) — an ordinary
insert into an existing table with an existing unique index (`[:provider, :kind, :foreign_id]`),
not a schema change. **Explicit check, as required**: no migration in B6a, B6b, or B6c touches
`book_targets`, `book_editions`, or `book_files` at the DDL level — every write goes through
existing Ecto insert/update against tables B4/B5 already created. `book_targets_profile_integrity_
insert`/`_update` fire only on `INSERT`/`UPDATE OF profile_id, media_kind` and only abort when
`profile_id IS NOT NULL` names a `media_profiles` row of the wrong `kind` — `adopt_work/3` never
sets `profile_id` at all (adoption of an already-correct file needs no acquisition profile, the
same reason `Catalog.find_or_create_at_available`'s `movie_attrs/1` never sets one either), so the
trigger's `WHEN` clause is false on every B6 write and never fires.

## What stays out

- **Audiobook adoption.** Every candidate B6 produces is `:ebook`; the audiobook Bookshelf instance
  (170 works, 651 editions, 1 M4B file, Audiobookshelf consumer) is untouched — no `MigrationSource`
  call targets it, no `book_targets` row of `media_kind: :audiobook` is created by any B6 code path.
  That is B7's, per the parity matrix's own `owner_milestone: B7` on both the "audiobook target and
  Spoken profile" and "Audiobookshelf filesystem and scan handoff" rows.
- **The B4-staging fallback for a candidate outside every configured root.** §0.2's judgment call:
  the existing Radarr/Sonarr migration code has no such branch either, the one real deployment gives
  no evidence it is needed, and `:outside_library_root` fails closed with a fixable operator error
  instead. If a real deployment ever needs it, that is new scope with its own evidence — not
  something to build speculatively now (AGENTS.md: "nothing speculative... no unrequested
  flexibility").
- **Calibre.** No B6 code path writes a Calibre database or invokes `calibredb` — the contract parks
  it entirely, and the observed topology (Booklore reading a filesystem root) never needed one.
- **Automatic format conversion or quality upgrades during adoption.** Every accepted file is
  adopted exactly as found; "Find a better match" (B5a) remains the only upgrade path, and it
  already works unmodified against a migration-adopted `:available` target.
- **Applying the dormant Bookshelf naming template.** `config/naming`'s
  `standardBookFormat` is read and may be shown informationally in preview (§B6b.1's `:profiles`/
  `:roots` snapshot fields), but B6 computes no path from it and renames nothing — "Preserve
  release filenames" is the locked B0 default, and Cinder's own dormant naming policy (whenever one
  ships) is a separate, explicit operator opt-in.
- **A second bulk-monitoring mechanism for fileless works.** The 661 monitored-no-file eBook works
  are deliberately *not* built into a new per-row migration UI — B5b's `preview_author_policy/2` /
  `apply_author_policy/4` already exist, already cap themselves, and become usable for a migrated
  author the moment B6c adopts that author's first work (§B6c.1.2's `import_resolution/1` call
  already stamps a real `openlibrary`/`hardcover` author identifier via `put_credits/3`, which is
  the only prerequisite `author_provider_reference/1` needs). Rebuilding that mechanism here would
  duplicate, not extend, B5.
- **An unattended background sweep for migration resolution** (the `BibliographyRefresher`
  pattern). B6's resolution loop is deliberately admin-driven and bounded per LiveView batch, not a
  `PollerSkeleton`-based unattended tick — this is a one-time cutover an operator actively runs, not
  ongoing monitoring, and giving it its own poller would add a second always-on process for a
  workflow that finishes in one sitting.
